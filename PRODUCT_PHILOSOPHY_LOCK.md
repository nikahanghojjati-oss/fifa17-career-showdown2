# Product Philosophy Lock — Private Two-Manager Companion

**Status:** Permanent owner decision [2026-08-16], priority clarification [2026-08-17]
**Authority:** This file + ROADMAP_AMENDMENTS.md §2 + POST_V1_ROADMAP_EXECUTION.md classification matrix + NEXT_TASK.md future-area list.

## Decision

Career Mode Showdown is a **private two-manager companion** for the owner and one friend.

- **Public community features are ELIMINATED** — not deferred; removed as product goals.
- **Global leaderboard / rankings are ELIMINATED** — same permanence.
- Future sessions must treat public community and global leaderboard work as **out of scope** unless the owner explicitly reverses this lock in a later roadmap amendment.

## Private remote joining priority

The friend joins from a different country; sessions are therefore remote. A workable **private remote joining / session system is a prioritized long-term product destination**, not an optional side feature and not a permanently blocked idea.

The feature is **dependency-gated and not yet implementation-authorized**. Its priority does not permit shortcuts. Every prerequisite required for a secure, recoverable private remote experience must be completed and proven before the Remote Joining runtime itself is implemented.

The ordered enabling path is:

1. preserve the proven local recovery, Save Library, identity and portability baseline;
2. establish Cloud / sync readiness with explicit revision, conflict, tombstone, recovery and provider boundaries;
3. establish private account / authentication / authorization identity without guessing local profile identity;
4. establish secure paired-device / private-session capability;
5. prove connected-rivalry synchronization, stale-write protection, conflict handling, offline/reconnect recovery and two-device behavior;
6. only then implement the private remote joining / session experience.

Priority rule: when the project reaches future networked work and no later owner instruction overrides this direction, the next safe prerequisite that materially advances this private Remote Joining path should be preferred over unrelated optional expansion. Each prerequisite still requires its own bounded implementation authorization in `NEXT_TASK.md` or a later explicit owner instruction.

This priority:

- strengthens the long-term private paired-device / Connected Rivalry direction;
- does **not** authorize cloud runtime, authentication, pairing, remote transport or Remote Joining today;
- does **not** authorize public communities, global leaderboards or any public-facing ranking/discovery surface;
- requires the complete prerequisite and infrastructure chain rather than rushing directly to multiplayer behavior.
