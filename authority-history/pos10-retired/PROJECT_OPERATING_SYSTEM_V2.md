# Career Mode Showdown Project Operating System v2

Status: current operating authority for project process and test classification.

POS v2 exists to make the project faster, safer and more product oriented. It preserves evidence and history without allowing continuity, historical wording, obsolete milestone gates or workflow topology to become a substitute for engineering.

## 1. Authority order

1. Later explicit owner instruction.
2. Current verified source, live GitHub state, provider state and deployed behavior.
3. Current machine-readable product authorities and evidence models.
4. Current task routing.
5. Historical handoffs, milestone records and provenance.

Historical prose never overrides current source.

## 2. Active product metrics

### SSJR

KEEP ACTIVE. Shared Showdown Journey Readiness measures accepted end-to-end two-manager product capability evidence. It remains the outcome/readiness metric for the current milestone.

### MDP

KEEP ACTIVE. Milestone Delivery Progress measures engineering lifecycle completion for the current milestone capabilities: design, implementation, automated verification, defect/review resolution, regression retest and product integration. MDP is planning/delivery maturity and never substitutes for SSJR production evidence.

### RJR-1

FREEZE AND ARCHIVE AS COMPLETED EVIDENCE. RJR-1 at 100/100 is historical evidence for shipped Remote Joining foundations. It must not be recalculated, re-earned or used as a normal current merge gate. RJR tests remain active only when they protect a still-used runtime/security/reconnect behavior. RJR wording, score narration, dated acceptance publication and old milestone routing belong to historical audit.

## 3. Session and continuity mechanisms

### ADB-1 Adaptive Debug Budget

KEEP ACTIVE. ADB-1 is the anti-spiral quality mechanism. It chooses an environment-specific failed correction/validation budget between 2 and 20. Narrow deterministic debugging with healthy context can receive a high budget. Broad failures, truncation, recovery, compaction, reconstruction, long-session risk or multiple unresolved lanes reduce it. The budget protects quality; it does not punish hard work.

Only meaningful failed correction/validation cycles consume ADB. Polling, reading logs, harmless wording cleanup and successful investigation do not consume attempts.

### SHP-2

COMPATIBILITY/DIAGNOSTIC ONLY. SHP retains useful context-health observations for legacy tooling, but its percentage is not a product metric and must not independently create routine engineering work. POS v2 decisions are based on actual context degradation plus ADB-1, explicit usage warnings and safe-boundary state. Future simplification may retire the visible percentage without losing ADB.

### HTR-1

ARCHIVE THE SCORE; KEEP THE FIVE-PART HANDOFF CHECKLIST. The useful concepts are durable state, authority snapshot, classified open work, successor execution contract and sealed transfer package. The 0/20/40/60/80/100 score has no product meaning and is not part of normal engineering reporting. Evaluate the checklist only when a real handoff is occurring.

### WEC

REMODEL AS MINIMAL RECOVERY STATE. Keep enough durable state to recover after interruption: exact repository/PR/head, current task, last safe checkpoint, blocker, next action and non-negotiable safety locks. Do not create standalone continuity PRs, repeated archive cycles or authority synchronization work unless a concrete recovery/publication hazard requires it.

### SLE

KEEP AS A PRINCIPLE, NOT A GATE. Smart Lean Efficient means load the minimum reliable context needed to resume correctly. Do not enforce exact wording, mirrored prose or packaging rituals in product CI.

### SNS

REMODEL. A successor snapshot is required at an actual handoff or recovery boundary. It should be compact, current and executable. Do not generate tiny SNS/VTLS files after every normal task and do not make routine product progress wait on documentation packaging.

### SNL

NO ACTIVE IMPLEMENTATION FOUND. Do not invent or gate on an SNL mechanism unless a concrete source artifact is later identified and reclassified.

## 4. Test classification

Every test or workflow belongs to one of four classes.

### A. Product critical: blocking

Protects current/future runtime behavior, UI/UX, data/storage, synchronization, recovery, authentication/authorization, privacy, provider/billing safety, executable schema/API authority, evidence validity or release/deployment correctness. Keep active.

### B. Current engineering quality: blocking when relevant

Protects integration behavior, syntax/build correctness, meaningful static architecture, browser journeys or regression behavior. Keep active, but deduplicate ownership so the same expensive suite does not run in multiple specialist workflows.

### C. Operations/continuity: non-blocking for product release

Protects ADB/WEC tooling, handoff generation or developer-process automation. Run explicitly with the operations audit when changing those tools. It must not turn unrelated product PRs red.

### D. Historical/provenance: archived/manual

Checks old PR numbers, dated milestones, old score narration, exact handoff wording, retired workflow topology or archival documents. Preserve files and evidence, but remove from automatic product CI. Run only when intentionally auditing history.

A test name containing Stage 2, Stage 3, Stage 4, Stage 5 or RJR is not enough to archive it. Classification depends on what behavior it protects today.

## 5. CI ownership

1. Stability owns the complete current product contract suite once.
2. Static App owns syntax, static release architecture and focused emulator safety. It must not repeat the entire current product suite.
3. Specialist security/provider/browser workflows own their specialist checks only. They must not append the full repository suite merely as reassurance.
4. Release burn-in repeats only the stateful integration journey needed for release confidence, not every contract family.
5. No gate may require an exact workflow count, exact number of YAML run blocks or historical topology.
6. Markdown-only and historical-only changes should not launch heavy browser/deployment proof unless the changed artifact is itself executable/current authority.

`CURRENT_PRODUCT_GUARDS.json` is the stable machine-readable summary. Active tests must prefer executable/config/source assertions over matching sentences in `NEXT_TASK.md` or handoff files.

Billing remains OFF. Firebase remains Spark. Blaze, Cloud Billing account linkage, Cloud Run and Cloud Functions remain forbidden. App Check enforcement remains OFF. Firestore browser persistence remains memory-only. Google Auth remains popup-only browserSessionPersistence with no extra scopes.

Exactly two private managers. Connected Rivalry pairing plus exact ACTIVE precedes league or club authority. Candidate C remains the sole destructive remote-to-local gameplay Apply authority with strict transaction-owned rollback. Canonical local storage keys remain the three approved keys. No public discovery, listing, lobby, matchmaking, community, rankings or global leaderboards.

`SSJR-DUAL-FULL-SCREEN-1` remains a product requirement: both legitimate managers individually experience every canonical shared gameplay screen.

## 7. Cleanup/archival rule

Never delete useful history merely because it is old. Remove obsolete material from active routing and compute first. Preserve it in Git history, existing authority-history/archive locations or explicit manual audit runners. Physical file moves are optional and should happen only when they do not break useful references.

Old open continuity-only PRs may be closed as superseded once verified not to contain unique current product authority. Closing preserves their full GitHub history.

## 8. Reporting under POS v2

Normal product reporting centers on SSJR, MDP, current lane, completed capability, blocker and next product unlock. Continuity health is reported when it materially affects the session, not as a competing product score.

At a genuine handoff, provide one compact successor snapshot with exact live state and next action. At normal checkpoints, prefer engineering progress over packaging.

## 9. Core rule

If a gate failure cannot plausibly change product behavior, safety, data, recovery, UI/UX, executable authority, evidence validity or release correctness, it is not allowed to block current product development merely because historical wording changed.
