# Career Mode Showdown Project Operating System v6

Status: candidate authority on the POS6 branch until reviewed and merged.

POS6 is Fast / Furious / Accurate. Its purpose is to increase real product throughput substantially by removing redundant execution, keeping every necessary product invariant under one clear owner, routing expensive proof only to the changed risk, and making developer-session continuity a tiny weighted recovery signal rather than a parallel project.

## 1. Authority

1. Later explicit owner instruction.
2. Current verified source, live GitHub state, provider state and deployed behavior.
3. `CURRENT_PRODUCT_GUARDS.json`, current product/evidence models and executable release authority.
4. `NEXT_TASK.md`.
5. Active PR recovery metadata when present.
6. A compact external developer relay only when a real transition occurs.
7. Git history for superseded operating systems and provenance.

Never combine validation evidence across heads.

## 2. Fast / Furious / Accurate

### FAST

Every non-document product change begins with one deterministic current-product census. Every blocking deterministic contract has one owner in `CURRENT_PRODUCT_TEST_MANIFEST.json` and executes once. POS6 operations tests execute only when operating-system code changes.

FAST is the cheapest high-information failure surface and should finish before expensive proof is interpreted.

### FURIOUS

RACE-6 classifies changed files and runs only the browser/emulator proof that can detect the changed risk. Current heavy domains are remote/security/provider, Shared Setup, storage/restore and visual/presentation. Independent implicated domains may execute in parallel.

### ACCURATE

Workflow, dependency, test-manifest, product-guard, release, service-worker, multi-domain and unknown non-document changes fail closed to a complete seal. Accuracy wins uncertainty.

Speed never comes from deleting a unique safety invariant. It comes from avoiding duplicate or irrelevant execution.

## 3. RACE-6 Risk-Adaptive CI Engine

`scripts/pos6-risk-router.mjs` is machine authority and `POS6_RISK_MAP.json` documents the policy.

- operating-only: operations tests only;
- documentation-only: no product CI;
- remote/session/provider: deterministic census + remote browser/emulator proof;
- storage/restore: deterministic census + storage browser proof;
- visual/presentation: deterministic census + visual browser proof;
- remote + storage: union of both risk lanes;
- release/core/workflow or three-plus product domains: ACCURATE;
- unknown: ACCURATE.

The router must be fail-safe. A new file category may make validation broader, never silently narrower.

## 4. One deterministic owner

All current blocking deterministic product contracts belong directly to `CURRENT_PRODUCT_TEST_MANIFEST.json`. The current product runner reports the complete failure census before returning red. Operations tests are not product tests. Historical/provenance and dormant architecture tests remain manual-only.

One invariant should not be executed repeatedly by Stability and multiple specialist workflows merely because historical workflow topology accumulated that duplication.

## 5. CWS-6 Continuity Weighted Signal

POS6 replaces activity-count and equal-weight transfer models with CWS-6. CWS-6 is a 0-100 engineering transition-risk score, not a session-progress meter.

Weights are machine authority in `POS6_CONTINUITY_MODEL.json`:
- recoverability / volatile-state risk: 35%;
- context-integrity damage: 25%;
- unresolved failure breadth/severity: 20%;
- concurrent mutation risk: 10%;
- adaptive-debug pressure: 10%.

Message count, tool-call count, elapsed time, successful reads, successful tests, ordinary polling and commit count have zero weight.

Decision bands:
- 0-44 `CONTINUE`;
- 45-64 `CHECKPOINT`;
- 65-84 `TRANSITION_AFTER_ATOMIC` when an atomic mutation is active, otherwise `TRANSITION_NOW`;
- 85-100 `TRANSITION_NOW`.

Hard safety floors override the weighted average when live authority cannot be resolved, crash-loss protection is exceeded, another AWU risks volatile-state loss, ADB-6 is exhausted, reconstruction damage is severe, or the owner explicitly requests transition.

A stale recovery checkpoint alone does not force transition. One complete AWU ahead of stale recovery state produces at least `CHECKPOINT`: refresh tiny PR metadata, then keep working.

## 6. Owner-facing continuity

Every completed substantive response ends with one concise line:

`Continuity: <DECISION> · <SCORE>/100 · <short dominant reason>`

The score is operational only and earns zero product credit. SSJR and MDP remain the product/delivery metrics.

The owner should not need to infer session health from conversation length or ask for a successor artifact preemptively. POS6 reports the decision directly.

## 7. AWU-1, CLB-1, recovery metadata and relay

POS6 keeps the crash-resistance mechanisms that worked:
- one coherent Atomic Work Unit per mutation lane;
- at most one AWU ahead of durable recovery state;
- tiny active-PR metadata stores branch/head, AWU, blocker class, last safe checkpoint, CWS-6 score/decision, next action and validation summary;
- recovery metadata is capped at 4 KiB and never changes the Git head or launches CI;
- an external developer relay file is generated only at a real transition and is capped at 8 KiB;
- no continuity-only commits or pull requests.

After an abrupt interruption, re-resolve live main/PR/head and resume from the recovery metadata. Do not recursively reload old handoff history unless an actual provenance question requires it.

## 8. ADB-6 Failure-Aware Adaptive Debugging

ADB-6 grants 3-20 meaningful correction/validation cycles according to failure class, breadth, context integrity, concurrent mutation risk and recoverability. Narrow test/process defects in healthy state may receive a high budget. Broad product/security failures and damaged/reconstructed context reduce it.

Only a meaningful correction followed by validation consumes a cycle. Reads, diagnosis, successful checks, ordinary polling and an unreproduced infrastructure flake consume zero.

FC-2/FC-3 style census comes first: diagnose the full coherent failure class before editing so the project does not rediscover one stale assertion per remote run.

## 9. Active GitHub Actions topology

Normal pull requests should converge toward one POS6 orchestrator rather than a large unconditional specialist matrix. Specialist proof remains available, but expensive lanes run only when RACE-6 identifies their risk or ACCURATE is required.

Main retains actual release/deployment proof. Product-release validation is not replaced by operating-system shortcuts.

## 10. Stale-system retirement

The active package command surface must not advertise WEC, SHP, HTR, old next-prompt, resume-capsule or handoff-preflight machinery. Superseded executable/process files may be removed from the current tree when POS6 provides the stronger replacement; Git history is the provenance archive.

SHP, HTR and WEC do not return as active decision systems. SNS/RCP-style recursive packages remain historical. Current recovery is PR metadata plus a compact relay file at an actual transition.
