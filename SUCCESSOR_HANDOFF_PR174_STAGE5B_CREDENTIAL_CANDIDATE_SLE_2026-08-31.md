## 3. Why Stage 5B was required

Stage 5A added a separate dormant private-session client and isolated candidate Rules. Its real Firestore emulator proved exact private capability/no listing, host-open, peer-join, terminal lifecycle and active account/device/rivalry denial boundaries.

The corrected Stage 5A Rules require `request.auth.token.device_id` to name the caller's current active registered device and bind mutations to that claim. Production Google tokens do not contain this claim. A browser-supplied device ID is not provider-verifiable identity, so production Rules publication could not safely follow Stage 5A.

Stage 5B therefore had one bounded task: determine and prove the smallest safe issuance, refresh and revocation mechanism without activating production infrastructure or weakening permanent locks.

## 4. Provider mechanism decision

Firebase user custom claims are user-wide. `setCustomUserClaims(uid, ...)` would make two browsers sharing one UID race over one device value. This is incompatible with simultaneous registered devices.

Firebase custom-token additional claims are per sign-in. The Auth Emulator proved two sessions for the same UID can retain different `device_id` and key-fingerprint claims across forced token refresh. Those per-sign-in claims also remained authoritative after a conflicting later user-wide claim was written.

The selected candidate therefore keeps the primary Google session for identity/reauthentication and uses a separate secondary custom-Auth session for exact device-bound Stage 5 access. Activation introduces custom authentication and remains a separately owner-authorized provider-policy change.

## 5. Browser device credential

`js/sparkDeviceCredential.js` is a dormant UMD/CommonJS module and is not loaded by production.

It provides:

- one ECDSA P-256 key pair generated by Web Crypto;
- a private key with `extractable: false` and `sign` usage only;
- dedicated IndexedDB database `careerModeShowdown.deviceCredential`;
- exact existing registered-device format `device_` plus 32 lowercase hex;
- normalized public JWK containing only `crv`, `kty`, `x` and `y`;
- stable SHA-256 fingerprint over the normalized JWK;
- conflict denial if another device ID attempts to reuse the stored key;
- exact canonical challenge payload;
- ECDSA P-256/SHA-256 proof;
- provider-result verification requiring `custom`, exact `device_id`, version, expiration and exact local key-fingerprint match.

It never writes localStorage or canonical Save storage. The non-extractable origin key is proof of possession, not hardware attestation; active same-origin compromise can still invoke it.

## 6. Trusted issuance and refresh protocol

`js/trustedDeviceCredentialIssuance.js` is provider-neutral dormant candidate source. It contains no Firebase Admin credential and has no production route.

Initial enrollment requires:

- a verified current Google principal;
- Google `auth_time` no older than five minutes;
- current active account;
- current active registered device;
- credential state `absent`;
- exact public JWK/fingerprint equality;
- a cryptographically random 256-bit challenge ID and 256-bit nonce;
- exact two-minute challenge lifetime.

Completion rechecks the Google principal, stored challenge, account/device/credential authority, JWK and fingerprint. It rejects extended/future/expired challenge state and verifies the ECDSA signature over the exact canonical payload.

The provider commit must atomically compare and preserve:

- account state `active`;
- device state `active`;
- challenge state `open` and exact expiry;
- expected credential state;
- expected active public-key fingerprint on refresh.

This prevents replay and concurrent active-key rotation. Only after a successful atomic commit may the adapter mint a Firebase custom token with exact additional claims `device_id`, `device_credential_version` and `device_key_sha256`.

An enrolled key may refresh through a new signed challenge even when the primary Google `auth_time` is older than five minutes. A custom-token principal cannot bootstrap or self-refresh its own privilege; the separate primary Google principal remains required.

## 7. Terminal revocation

Revocation requires a current Google principal with recent authentication. It does not require the target private key so a lost or compromised device can be revoked from another authenticated device.

The provider adapter must atomically compare active account/device/credential state and the exact enrolled fingerprint, then set both the registered-device state and credential state to `revoked`. Successful terminal replay is idempotent.

Stage 5A candidate Rules re-read the registered-device document on every session operation. The integrated emulator proves an already-issued Device B token is denied immediately after Device B document revocation while Device A for the same UID remains authorized.

Credential-only revocation while leaving the registered device active is an inconsistent and rejected state because already-issued ID tokens would otherwise remain accepted until expiry.
