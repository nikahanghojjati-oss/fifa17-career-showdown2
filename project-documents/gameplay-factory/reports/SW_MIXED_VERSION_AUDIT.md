# JOB-1650 — Service-worker mixed-version audit

**Result: 4 of 5 scenarios have a conditional route to mixed release bytes; 1 does not.** This is a static, report-only audit, **not** a reproduced browser failure. The four "can mix" results require conditions noted below (such as non-atomic publication, activation with another tab open, or changed image bytes at an unchanged URL). The intended, completely cached CSS/JS route is revision-pinned.

**Read from:** `service-worker.js` and `js/offlineApp.js` on `gameplay/bug-list-1`. Cross-checked the HTML revision pin in `index.html` and optional loader in `js/optionalModules.js` on the same branch. **Report written to:** `factory/gameplay-v1`. Line numbers below refer to the source branch.

## What the worker currently guarantees

- `service-worker.js:1-7`: `RUNTIME_REVISION = "1.9.1-r70"`, `PREVIOUS_RUNTIME_REVISION = "1.9.1-r69"`; shell, runtime-mode and on-demand image caches are named by revision.
- `service-worker.js:244-245,274,281-291,315`: on **install**, fetch the `SHELL_PATHS` list with `?v=r70` and `cache: "reload"`; `cache.addAll` and `verifyCache` require successful entries for all listed paths, and delete the new cache if population fails. **Verification checks response presence/OK, not revision identity, MIME type or content hash.** A 200 response with bytes from a different release can pass.
- `service-worker.js:320,324`: manual activation verifies the current shell before `skipWaiting()`. On **activate**, it verifies again, clears forced rollback, retains the current shell and one recovery shell, prunes other shell/mode/image caches and calls `clients.claim()`. Keeping the *named* previous revision is intended, not unconditional: `findRecoveryRuntime` must find it valid first.
- `service-worker.js:255-272,281-286`: `verifyCache(r69)` uses the **current r70 `SHELL_PATHS` list**. If the older release legitimately lacked a newly added r70 path, it may be rejected and deleted. The generic older-revision fallback only checks `index.html`, not the whole older asset set. This can cause rollback or loading failure without necessarily mixing bytes.
- `service-worker.js:300-305,339-347`: **navigation** chooses forced rollback, else verified current, else recovery, and returns the chosen cached `index.html`. A non-navigation request with `?v=<revision>` is answered **only** from that revision's cache, otherwise `Response.error()`. No versioned CSS/JS fallback to the latest network release occurs.
- `js/offlineApp.js:1-4,163-178,429-471,473-495,512-544,601-608`: the page reads its `app-asset-revision` meta; its offline CSS gets that revision; a waiting worker is activated at a safe UI boundary; manual activation causes a reload on `controllerchange`; rollback requests the old shell then reloads. An **unsolicited** controller change only re-verifies readiness, not reload. `index.html:6,11,410-416` and `js/optionalModules.js:1-20,23-40,92-105` pin the main and optional CSS/JS requests to the document revision.
- **Exception:** `service-worker.js:330-337,346` processes `visual-assets/v10_1/` images *before* consulting a request's `?v`; `v10ImageRevision()` chooses the worker's **current** revision unless a global rollback override exists, not the requesting page's revision. An uncached image is fetched at its path from the network and saved into that selected image cache. Additionally `service-worker.js:12-23,346` deliberately bypasses shell caching for runtime configuration/bootstrap and some network-only scripts.

## Five requested cases

| Case | Can old/new release bytes mix? | Evidence, exact mechanism |
| --- | --- | --- |
| **(a) Normal update while app closed** | **YES, conditional on non-atomic or inconsistent deployment; normally NO if all origin bytes belong to one release.** | `service-worker.js:274,288-291,315` fills the r70 cache by fetching all URLs, but `281-286` merely checks `response.ok`. If r70 HTML and an older CSS/JS body are served during a staggered publication (even under `?v=r70`), the worker can install a nominally complete but mixed cache, then `324,344-347` serve it. A fully published, immutable release does not suffer this path. |
| **(b) Update arrives while app open** | **YES, conditional on activation while another old tab/client remains open.** | While the new worker is only **waiting**, the old page remains on the old revision. Once `CMS_ACTIVATE_UPDATE` calls `skipWaiting()` (`service-worker.js:320`) and activation calls `clients.claim()` (`324`), an old tab can keep its old DOM: `js/offlineApp.js:601-608` reloads only if *that tab's* `activationRequested` is true. Its `?v=r69` CSS/JS still read the retained r69 cache (`service-worker.js:346-347`), but a subsequent V10 image request reads the **r70** image cache or current network bytes (`330-337`). The bytes only visibly differ if that image URL was changed in place. Network-only/config exceptions can also supply current files to an old tab. |
| **(c) Player reloads mid-update** | **YES, conditional on a controller switch between the navigation and later requests.** | Navigation chooses one cached `index.html` at `service-worker.js:300-305,341-345`, but this does not bind the whole navigation's resources to a client-specific worker revision. If activation/claim intersects the reload, CSS/JS are still protected by their explicit `?v` and retained cache (`346-347`), while later image requests select the now-active worker's current image revision (`330-337`) rather than the document's revision. If no controller switch or changed image URL occurs, there is no mixed display. A non-retained old revision instead yields failed assets. |
| **(d) Rollback copy used** | **YES, on an uncached prior-version image whose same URL now has different bytes (or a network-only file).** | `service-worker.js:321,300-304` records the forced previous revision and returns its cached HTML; `js/offlineApp.js:473-490` reloads; revision-tagged CSS/JS remain in its retained shell cache. But `service-worker.js:331-337` fetches any absent previous-version image from the **live** path, stores that response in the previous image cache, and can thereby combine old HTML with new art. `service-worker.js:346` bypassed dynamic files likewise need separate compatibility handling. Offline, the image miss instead fails; there is no current-version network response to mix. |
| **(e) A file request fails offline** | **NO new mix caused by failure; availability may fail.** | A missing `?v=<revision>` asset returns `Response.error()` (`service-worker.js:325,346-347`) rather than another version; a missing image's `fetch(request)` (`335`) rejects offline; and if neither navigation cache is valid, the navigation network fallback (`344`) fails. The code does **not** silently swap in an alternate-version CSS/JS file. An already mis-cached file from (a) is a preexisting integrity problem, not an offline fallback. |

## Smallest fixes in words (no code changed)

1. **Close the install-integrity gap (case a):** Publish each release's immutable assets before exposing its new worker, and verify a revision-specific asset manifest/content hashes before accepting a cache as complete. Query-string `?v` plus HTTP 200 alone cannot prove the bytes are for r70. Reject or hold the worker when content does not match.
2. **Pin image requests to their document (cases b/c/d):** Attach the **page's** runtime revision to V10 image requests and make the image fetch handler honor it *before* selecting an image cache, with per-revision cache keys. A rollback image absent from that revision's cache should be available from immutable revision-specific asset URLs or be reported missing; never silently fill a previous-revision cache from a mutable latest-release URL. If asset paths are truly immutable across releases, enforce and test that guarantee; the current code's comment is not a hash check.
3. **Handle all open clients on activation (cases b/c):** Coordinate upgrade across tabs. Do not claim/revision-switch a still-rendering old client without either pinning **all** its resource requests or arranging a guarded refresh of every controlled tab. The initiating tab's `activationRequested` flag does not cover other tabs. Preserve in-progress work while deferring upgrade.
4. **Make recovery verification revision-specific (rollback reliability):** Retain the old shell against its **own** recorded `SHELL_PATHS` manifest. Never consider a generic recovery cache complete after checking only `index.html`. This prevents a rollback that renders HTML but lacks its CSS/JS; that failure is distinct from mixing.
5. **Review intentional bypasses:** Runtime config, App Check bootstrap and network-only acceptance scripts are current-network resources by design (`service-worker.js:12-23,346`). If they must work with older HTML, define backward compatibility; otherwise gate them to an explicit compatible version. Do not indiscriminately freeze security configuration.

**Scope and caveat:** This is source-level reachability analysis. No production network trace, version-to-version binary comparison, two-tab browser reproduction or live deployment test was run. **Count: 4/5 potentially mix, all conditional; 1/5 does not introduce a mix on offline failure.**
