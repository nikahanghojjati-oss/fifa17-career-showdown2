## Finding 1 — SURE: early stylesheet failures escape their caller

- File and lines: `js/optionalModules.js:63, 73, 87–88` in the audited base; the shared stylesheet loader is in the assigned first half.
- What the player sees: while opening Statistics with an interrupted stylesheet download and a slower script download, the application shows the generic “An unexpected application error was detected” notice before the normal module-open failure report. If a script fails first, the sibling stylesheet rejection may never reach the caller at all. This is an expected asset failure escaping as an unhandled application error.
- Why: the loader returns a rejecting promise with no immediate rejection observer. Its callers start styles concurrently but wait for script loading before awaiting the style. The real application boundary handles `unhandledrejection` as an unexpected application error.
- Code (three lines from the base):
  ```js
  reject(new Error(`Unable to load ${path}.`));
  runtimeStylePromises.set(key, promise);
  return promise;
  ```
- Smallest change: attach `promise.catch(() => {});` immediately after caching the style promise. Return the original promise, so the normal caller still receives exactly the same rejection. Error/timeout cleanup, cache deletion and retries remain intact. Removed the nonessential “starters done” comment to preserve the tight startup gzip budget; no executable statement was removed.
- Uncommitted Node repro calls the real `openOptionalModule('careerStatistics')`, real stylesheet loader and real Statistics script loader, with required football presentation already ready. It fires the real stylesheet error listener while the real analytics script is pending, then completes the expected script APIs.
- Repro output before the fix:

  Screen opened: false
  Handled open errors: 1
  Unhandled reasons: Unable to load css/analytics.css.
