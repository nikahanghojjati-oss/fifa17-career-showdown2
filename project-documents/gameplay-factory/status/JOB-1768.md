## Finding 1 — a retained Setup from a different rivalry can supply the score
- **File and line:** `js/productionSharedCanonicalScoring.js:57-60` (before fix, provider options did not compare the requested rivalry with the Setup rivalry).
- **What the player sees:** During a rivalry/save switch, a briefly held confirmed Setup from the earlier rivalry may cause the current rivalry's Season Review to show the other rivalry's scores and season winner. Setup intentionally holds its last confirmed state for one failed refresh.
- **Why:** The scoring request takes its rivalry from the currently open Showdown but provider options independently take `setup.rivalryId` without checking that it matches. Original lines:
  ```js
  const setup=setupApi?.getState?.();if(!setup||setup.ready!==true||!setup.setup||setup.setup.phase!=="SHOWDOWN_CONFIRMED"||setup.setup.revision!==6||!setup.rivalryId||!setup.sessionId||!setup.deviceId)pcscFail("CANONICAL_SCORING_SETUP_NOT_CONFIRMED");
  const services=await root.CareerModeProductionFirebaseRuntime.ensureAccountServices();if(!services||services.ok===false||!services.auth?.currentUser||!services.firestore||!services.firestoreSdk)pcscFail("CANONICAL_SCORING_PROVIDER_UNAVAILABLE","Connected account services are unavailable.");
  ```
  The returned provider projection carries a season number but no rivalry identifier, so the adapter otherwise stamps the current rivalry onto whichever Setup supplied the read.
- **Smallest change:** Add `if(String(setup.rivalryId)!==request.rivalryId)pcscFail("CANONICAL_SCORING_CONTEXT_STALE");` before the provider read. The existing retry treats context-stale reads as quiet and can retry after Setup catches up.
- **Confidence:** **SURE** — the read options previously used the retained rivalry with no equality guard, and the adapter would accept a same-season projection and label it as the current rivalry.
