## The bug
In every CE2PG run (r74 and r75), Nik's Shared Setup write at the league-and-clubs step is refused:
`evaluation error at L2800:26 for 'update' @ L2800, false for 'get' @ L2697, false for 'get' @ L2707, evaluation error at
L2739:21 for 'get' @ L2739, evaluation error at L2867:23 for 'get' @ L2867`. (Generated rules file
`firestore.spark.generated.rules`; L2800 is `rivalries/{id}/sharedSetup/authoritative` `allow update: if ssjrValidUpdateLedger(rivalryId)`;
L2697 accounts get, L2707 devices get, L2739 rivalry get, L2867 sessions get.) The game recovers on a retry, which costs reads
and writes from the free daily limit and slows setup.

## What Claude already found (confirm first)
The commit holds the sharedSetup write plus "verify" entries for the documents the transaction only read: account, device,
rivalry, session. Firestore evaluates every one of their read rules in the same request and they share one expression and
get() budget with the write rule (`ssjrWriteAuthorityValid`, generated ~L925, does 5 get() calls and `ssjrActorRole` twice).
Likely the same root cause as JOB-1803 (terminal close). Unexplained so far: why `false for 'get' @ L2697` on Nik's OWN account
(rule `signedIn() && uid == accountId`); probably the shared budget is already used up when it is evaluated. Prove or disprove.

## The fix to try
Find the Shared Setup ledger transaction (search `sharedSetup/authoritative` and `runTransaction` in `js/`; start with
`js/sparkSharedShowdownSetup.js`, then `js/productionSharedShowdownSetup.js`). Read the account, device, rivalry and
session documents BEFORE the transaction with plain reads, and keep inside the transaction only the document it writes. Same
values, same order of checks, nothing less safe (the write rule still re-checks with get()). The Rules must NOT change. Keep the
Firestore budget test passing and report reads/writes per season before and after from the CE2PG `network` section.
