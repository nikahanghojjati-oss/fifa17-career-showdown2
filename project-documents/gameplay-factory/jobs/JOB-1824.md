## Why
The live game runs on Firebase's free plan: at most **50,000 document reads and 20,000 document writes per day** for both players
together, reset at 3 am Boston. Nik wants a reliable answer to "how many seasons can we play per day before the game stops?",
measured over enough play to trust, **without touching the live game or its free allowance**. Everything here runs on the local
Firebase emulators with the demo project `demo-cms-browser-journey`. Never use a real Firebase project, never sign in to Google,
never deploy.

## Tools you start from (already built by Claude for release r75)
Branch `tools/firestore-meter`, folder `tools/firestore-meter/` (read `README.md` and `RUN.md` there):
- `firestore-wrapper.js` is served in place of the Firestore SDK module and reports every document read and write, including
  transaction reads and listener deliveries, through the `__cmsMeterEvent` binding.
- `meter-journey.cjs` lines ~106-135 show the three `context.route(...)` calls and the `exposeBinding` that install it, and
  `park()` shows how idle windows were recorded.
- `report.js` / `analyze.js` / `perwin.js` summarize a meter JSON. `run60.analysis.txt` is sample output (r74 code, before the fix).
- How writes are counted (the same rule the r75 measurement used): each committed document **plus each transaction
  "verify" entry** (a document read inside a transaction but not written is billed as a write).

The two-player game itself is driven by the CE2PG harness: `git fetch origin gameplay/ce2pg && git show
FETCH_HEAD:tests/browser/ce2pg-journey.cjs > tests/browser/ce2pg-journey.cjs` (JOB-1802 ran it in Codex: Java 21,
`npm i --no-save --package-lock=false firebase@12.17.0`, Chromium, static server on port 4511; a 3-season run took ~18 min).

## What to do
1. **Add the meter to a copy of the CE2PG harness** (`tests/browser/ce2pg-meter.cjs`): the same routes and binding as
   `meter-journey.cjs`, every event tagged with the manager and the current season, phase and screen. Keep every CE2PG check.
   Also add `METER_IDLE_MS` (default 0): after each season's results are saved, park both managers for that long on each of
   **Showdown Home, Standings, Season Results**, then once more with Nik's game tab hidden: open a second page in his browser context with `context.newPage()` and
   `bringToFront()` it, check `document.visibilityState === "hidden"` in his game tab, and record that check.
2. **Check the meter is honest** before the long runs: one 1-season run; compare its counted reads and writes with the r75
   report's per-season figures (a 3-season Showdown, both players: about 1,261 reads and 410 writes). Explain any big gap.
3. **Runs** (sequential, never in parallel), on the code branch named above:
   | Run | Seasons | METER_IDLE_MS |
   | --- | --- | --- |
   | m1 | 1 | 0 |
   | m3a | 3 | 0 |
   | m3b | 3 | 0 |
   | m5 | 5 | 0 |
   | m10 | 10 | 0 |
   | i3 | 3 | 300000 (5 min per wait screen) |
   If time runs short, drop m5 first, never m10 or i3.
4. **Rules lookups.** Firestore Rules `get()`/`exists()` calls are billed as reads but a client meter cannot see them. After one
   run, try the emulator's coverage report `http://127.0.0.1:<firestore port>/emulator/v1/projects/demo-cms-browser-journey:ruleCoverage`
   and count `get`/`exists` evaluations. If you cannot get it, say so and add 25% to reads as headroom in the prediction.
5. **Numbers to compute** (both players together, per season):
   - reads, writes, transactions, listener deliveries: mean, lowest and highest across runs, and per season number
     (season 1 vs later seasons vs the final season with the close);
   - the five biggest sources (owner module from the event's call chain) of reads and of writes;
   - idle cost from i3: reads and writes **per minute** on each wait screen, visible and hidden.
6. **The prediction table.** Real seasons take time, and the game sits open while the players play FIFA. For each of
   **30, 60 and 120 minutes** of open-tab waiting per season, compute:
   `reads/day per season = reads per season + idle reads/min × minutes` (same for writes), then
   `seasons per day = min(50,000 ÷ reads, 20,000 ÷ writes)`, with the low and high from your runs, and say which limit runs
   out first. Also give the plain answer: "With about an hour of waiting per season, about N seasons a day fit."
