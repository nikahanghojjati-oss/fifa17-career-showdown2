## Bug
`js/sparkSharedTransferChallenge.js:149` (`stspMutate`) computes `operationHash=stspHash({actorRole,type,operationId,baseRevision,...normalizedPayload})` and stores it in the shared public ledger (`operationHashes`), which the rival can read. For a guess lock, the payload is the guess list. Every other input is public and the guess space is small (leagues and nationalities), so a rival with browser dev tools can hash every candidate list and learn the opponent's guesses before signings lock.

## The change
- The public ledger must not hold any value derived only from private payload plus public inputs. Pick the smallest safe design and explain it in the PR. For example, hash only the public fields into the public ledger and keep the full-payload hash (for idempotency conflict detection) in the actor's own private document. Another option is a per-operation random salt stored only in the actor's private document.
- Replays of the same operation must still be accepted, and a conflicting replay must still fail with `TRANSFER_IDEMPOTENCY_CONFLICT`.
- Keep the ledger's `HASH` format, so no Firestore Rules change is needed. **If the design truly needs a Rules change, stop and report.** Rules changes need Nik's approval.
- Old ledgers written by r66 clients must still read.

## Proof
- New contract `tests/contracts/job-1051-transfer-ledger-privacy-contracts.cjs`: given a public ledger after a guess lock, brute-forcing every guess list from the catalog never matches the stored public hash, and the idempotent replay and conflict cases still behave.
