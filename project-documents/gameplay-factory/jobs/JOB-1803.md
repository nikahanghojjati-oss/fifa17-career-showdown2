## The bug
In every CE2PG run (3 and 10 seasons) one of Nik's writes at the end of the Showdown is refused by Firestore with
`maximum of 1000 expressions ... for 'update' @ L2741` (line numbers are in the generated rules file
`firestore.spark.generated.rules`, built by `node scripts/build-production-firestore-rules.mjs && node scripts/build-production-firestore-rules-with-persistent-pair.mjs`).
The Champion screen still appears because a retry or Daniel's write succeeds, but every refused write costs reads and writes
from the free daily limit, and on a bad connection the close can stall.

## What Claude already found (Claude did not finish; confirm before you rely on it)
- The refused commit is the FIRST terminal-progress transaction, `stcAdvanceProgress` in `js/sparkTerminalClose.js:40-46`
  (season 1), not the final close. Its commit contains the rivalry write plus "verify" entries for every document the
  transaction READ but did not write: `accounts/<uid>`, `devices/<id>`, `rivalries/<id>/sharedSetup/authoritative`,
  `rivalries/<id>/seasonCommits/season_1`.
- Firestore evaluates the **read** rule of every verify entry in the same request, and they share ONE 1000-expression budget
  (and the 20-call get() budget) with the write rule. The read rules are expensive: `ssjrEntitled` -> `activePairedRivalry`
  (generated ~L449) does `get(rivalry)` and `activeAccount` twice; `currentlyEntitled` (~L442) and `sessionCanRead` (~L831)
  call `activeActor`, `activePairedRivalry` and `exists()`. The write rule alone fits; with the verify reads it goes over.
- The emulator error lists: `false for 'get' @ L2697` (accounts), `evaluation error at L2797:23` (sharedSetup get),
  `evaluation error at L2858:23` (seasonCommits get).
- The Rules must NOT change in this job (a Rules change needs a production deploy and a fixture sign-off).

## The fix to try
In the app code, read the documents that the transaction only needs to *look at* (account, device, sharedSetup, seasonCommit)
**before** the transaction with plain document reads, and keep inside the transaction only the document it writes (the
rivalry, which needs the compare-and-set). The write rule already re-checks the account, device and setup with `get()`, so
nothing becomes less safe. Keep every value the transaction used to compute from those documents exactly the same.
Check `js/sparkPrivatePairing.js` (the "Firestore budget layer (r75)" at the end) to see how reads outside transactions are
cached; your change must keep `node tests/contracts/firestore-budget-contracts.cjs` passing and must not add reads per
season (count them before/after with the CE2PG report's `network` section and state both numbers).
Look for the same pattern in the other close-path transactions in `js/sparkTerminalClose.js` and
`js/productionSharedTerminalClose.js`; fix them the same way only if CE2PG shows them refused.
