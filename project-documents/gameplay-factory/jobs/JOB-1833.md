## Why
PR #863 (JOB-1829) stops the Transfer Challenge screen re-reading unchanged documents. Two parts are good and stay: the per-
transaction memo in `js/sparkSharedTransferChallenge.js` `stspRead`, and reusing Setup/Career on plain presentation refreshes.
Claude's check found three problems in `js/productionSharedTransferChallenge.js` and a misleading test. Full report:
`/mnt/project-files/gameplay/r76/verify/PR-863.md`.
1. **New raw Firestore listeners (`pstcEnsureCoverage`)** on `rivalries/{id}` and its session doc call the SDK directly, outside
   `CareerModeFirestoreBudget.watchWaitPoint`. The budget already reuses rivalry and session for 60 s in that state, so they save
   almost nothing, cost 2 reads per attach and re-attach on every wait, tab hide/show and authority-key change. The PR's own partial
   meter shows rivalry reads going UP (14 -> 22) and session reads UP (14 -> 17).
2. **New view wipes.** The `career-mode-firestore-authority-denied` listener (about line 419) and the authority-key checks (about
   lines 51 and 127) call `pstcClearCachedContext()` (view=null, openedKey=""). That event fires on any permission-denied in the app,
   including the Rules-rejected loser of a simultaneous tap; the key includes `device.registered`, which goes false on a short pairing
   error. After a wipe the timer shows 15:00 mid-window, the fast check is released, typed text is not saved as a draft, and the
   next render clears both roles. None of this happens on r75.
3. **REFRESH SHARED CHALLENGE** can return a cached result up to 15 s old. On r75 it forced a fresh read.
4. The new test stubs `CareerModeFirestoreBudget` as a pass-through (`services:s=>s`), so "52 -> 8 reads" is measured against a
   setup that reuses nothing, not the live game.
