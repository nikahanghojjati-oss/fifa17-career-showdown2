## Why
JOB-1824 (PR #851, `reports/firestore-meter/R76_FIRESTORE_METER.md`) measured r75 on the emulator: the game's own reads are
about 450 and writes about 140 per two-player season, but the Firestore Rules run about **10,000 `get`/`exists`/`getAfter`
evaluations per season**, plus about 250 per minute while both managers wait. 1824 charged every evaluation as one read, which
gives about 2 seasons a day. Firebase bills a Rules lookup as one read **per distinct document per request** (looking up the
same document again inside the same request is not billed again). So the real cost sits somewhere between 450 and
10,000 reads per season. Nik needs **20 to 30 seasons a day** (at most about 1,700 to 2,500 reads per season, waiting
included). This job finds the exact billable number and the biggest causes, so Claude can cut them in r76.

## What to do
1. **Map every request the game sends in a season.** From one `m3` run (3 seasons, `METER_IDLE_MS=0`) and one `i3` style run
   (3 seasons, `METER_IDLE_MS=120000`), group the requests by kind: collection/document path pattern, operation
   (get, list/query, listen, transaction read, transaction commit, batched write) and owner module (as in 1824).
2. **For each request kind, list its Rules lookups.** Read the composed Rules: for the `match` block and operation that
   request hits, list every `get()`/`exists()`/`getAfter()` it evaluates (Rules file:line and the document path it reads,
   for example `/accounts/{uid}` or `/showdowns/{id}/devices/{d}`). Count the **distinct documents** per request, since that is what
   Firebase bills. Check the count against the emulator's coverage counters for that kind, as 1824 did: run a short script that
   sends just that request kind N times and compare.
3. **Billable reads per season** = client reads + the sum over request kinds of (count × distinct Rules documents). Give it per
   season position (first + setup, later, final + close) and per minute on each wait screen (Home, Standings, Season Results).
   Then redo 1824's prediction table (30 / 60 / 120 minutes of waiting) with this billable model next to 1824's upper model.
4. **Top 10 causes,** ranked by billable reads per season: request kind, owner module + function (file:line), count per season,
   distinct Rules documents each, total.
5. **A cut for each of the top 10,** with the reads it would save per season. Two kinds, and say which each one is:
   - **App side** (no Rules change): send fewer requests. Examples: a read-only transaction that only checks state can become a
     plain read or reuse the listener's latest snapshot; two transactions in a row on the same Showdown can become one; a check
     the game already knows the answer to can be skipped.
   - **Rules side** (needs Nik's sign-off): a lookup that can be replaced by a field already on the document being read or
     written, or by `request.auth` data, or a helper that looks up the same document through two different paths.
   Never propose removing a protection: every cut must keep the same people allowed and the same people refused. Say for each
   Rules-side cut which existing Rules test proves that.
6. **The plain answer:** "Billable today: about N reads per season, about M seasons a day at 60 minutes of waiting. With the
   app-side cuts: about A a day. With app-side and Rules-side cuts: about B a day."
