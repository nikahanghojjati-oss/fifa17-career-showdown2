# Hunt 1018 · Sessions, pairing and reconnect

Can this chat run node: yes (`v24.19.0`).

## Flow map
1. Google popup sign-in resolves Connected Account with browser-session auth persistence.
2. OnlinePlayerIdentity keeps the chosen Daniel/Nik role in IndexedDB, keyed to the account.
3. PrivatePairing registers a random IndexedDB browser device under that account.
4. Daniel prepares an empty shared local save with 1, 3, 5 or 10 seasons.
5. PersistentNikDanielPair puts season length into the pairing capability and creates a 15-minute invite.
6. The pairing transaction also writes the account pairLink and career index through a durable witness.
7. Nik pastes the wrapped code; a matching empty local save is provisioned before redemption.
8. Redemption atomically fills playerTwo, activates the rivalry and writes Nik's durable witness.
9. Daniel's pending-pair poll reads every 4 seconds, later every 15 seconds; hidden tabs pause reads.
10. Continue Career switches to the exact provider-bound local save and attaches its rivalry pointer.
11. Entry requires account, registered device, attached rivalry and an exact unexpired ACTIVE session.
12. RemoteJoining resolves private dependencies; host creates a session capability kept only in page memory.
13. StandardAuthPrivateSession delegates to PrivateSession with registered-device metadata authority.
14. Host opens a session for four hours minus one minute; peer join changes OPEN to ACTIVE.
15. The host join watcher reads OPEN sessions every 4 seconds for up to 10 minutes.
16. Pending host/join/close outcomes retain the exact capability for deterministic retry.
17. NEW SESSION CODE closes a held ACTIVE session before hosting or joining a replacement.
18. Reconnect observes offline/pending/fresh-session states and validates setup and season progress.
19. Reload drops session memory; shared local saves and account pair links remain.
20. A fresh browser needs the exact local recovery copy; a third account has no rivalry entitlement.
