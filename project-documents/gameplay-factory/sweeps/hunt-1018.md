### H1018-1 Double-tapping replacement host creates two fresh session capabilities
severity: S1
status: CONFIRMED (repro below)
where: js/sparkRemoteJoining.js:122-130 (srjEndHeldSession), 211-221 (srjHostSession), 329-333 (replacement host button)
steps: 1. Both managers hold an ACTIVE private session. 2. Open NEW SESSION CODE and tap HOST NEW SESSION (REPLACES CURRENT) twice while authority resolution is awaiting. 3. One close accepts and the other replays; both continuations host a different replacement. 4. If Nik takes the first displayed code before the second completes, Daniel's final page-memory pointer is to the other OPEN session.
expected: One replacement action owns the whole resolve/end/start interval; the second tap is rejected or shares the first promise and produces the same capability.
actual: busy remains false before srjEndHeldSession's first await. Both replacement guards pass, and both fresh host writes succeed. Only one sessionId remains in page memory. Nik can be ACTIVE on the first while Daniel waits OPEN on the second; he cannot proceed on that session until the managers exchange another code or explicitly recover.
repro: sweeps/repro/hunt-1018.cjs (replacementRace). Output: `H1018-1 FAIL replacement busy initially=false; successful hosts=2; OPEN provider sessions=2`.
fix idea: Acquire one action lock synchronously before any replacement await and hold it until end plus host/join finishes. Bind each continuation to its captured operation/context.

### H1018-2 Replacing an OPEN session loses the host join watcher
severity: S2
status: CONFIRMED (repro below)
where: js/sparkRemoteJoining.js:184-199 (srjWatchForJoin), 171 (host success watcher), 277-290 (revoke path)
steps: 1. Host session A; its 4-second watcher is scheduled. 2. Before that timer fires, use HOST NEW SESSION (REPLACES CURRENT) to revoke A and open B. 3. Nik joins B. 4. The old timer fires.
expected: The watcher follows B and observes Nik's ACTIVE join, allowing the host's normal automatic return to the journey.
actual: B's watcher call exits because srjJoinWatchTimer still belongs to A. A's callback clears the timer slot, sees that A is no longer held, and returns before rearming. No watcher remains. Provider B is ACTIVE but the host stays OPEN with stale waiting state; REFRESH / READ is a manual workaround.
repro: sweeps/repro/hunt-1018.cjs (replacementWatcher). Output: `H1018-2 FAIL provider fresh=active; host=open; remaining watcher timers=0`.
fix idea: Cancel/rebind the old watcher on session replacement; track its sessionId and start time rather than only a global timer handle.

### H1018-3 Signing out keeps an already recovered journey authoritative
severity: S2
status: CONFIRMED (repro below)
where: js/productionSharedJourneyReconnect.js:39-46 (pjrCurrentIdentity), 156-159 (PJR_PENDING_AUTHORITY_CODES / pjrRefresh)
steps: 1. Recover a nonterminal shared journey with an exact ACTIVE session. 2. Sign out or lose account/device/rivalry authority. 3. Refresh recovery more than once.
expected: Keep the durable plan/history, but clear recovered and activeAuthorization until the signed-in identity is verified again.
actual: pjrCurrentIdentity throws JOURNEY_RECONNECT_AUTH_REQUIRED. The catch treats it as quiet pending and returns the old state forever. It never publishes a non-authoritative state. The ACTIVE_RECOVERED banner and isRecovered() remain true while the account is disconnected. The same branch handles revoked/unregistered device and detached rivalry. This is a stale client-authority claim; the repro does not demonstrate a provider-access bypass.
repro: sweeps/repro/hunt-1018.cjs (logoutRetainsAuthority). Output: `H1018-3 FAIL account connected=false; phase=ACTIVE_RECOVERED; activeAuthorization=true`.
fix idea: Publish a held state with activeAuthorization/recovered false on authority loss, preserving verified durable history separately. Distinguish initial pending identity from losing authority after recovery.

### H1018-4 An in-flight recovery refresh overwrites OFFLINE_HOLD
severity: S2
status: CONFIRMED (repro below)
where: js/productionSharedJourneyReconnect.js:126-150 (pjrOfflineHold / pjrRefreshNow), 168 (offline listener)
steps: 1. Start a refresh from ACTIVE_RECOVERED while online. 2. While setup/progression reads await, go offline. 3. The offline listener publishes OFFLINE_HOLD. 4. The outstanding read completes successfully (for example a response already in flight).
expected: The offline event invalidates the older refresh. OFFLINE_HOLD and activeAuthorization=false remain until a new online verification.
actual: The successful continuation uses base.networkOnline=true captured before the awaits, without checking the current navigator or an operation generation. It publishes ACTIVE_RECOVERED over OFFLINE_HOLD, including networkOnline=true although navigator.onLine is false. A later poll may repair it; the invariant is false during that interval.
repro: sweeps/repro/hunt-1018.cjs (offlineDuringRead). Output: `H1018-4 FAIL navigator.onLine=false; phase=ACTIVE_RECOVERED; networkOnline=true`.
fix idea: Invalidate in-flight refreshes on offline/context changes and recheck current network/authority before publishing success.

### H1018-5 A successful delayed read recovers a session after its expiry
severity: S2
status: CONFIRMED (repro below)
where: js/productionSharedJourneyReconnect.js:139-150 (pjrRefreshNow)
steps: 1. Refresh shortly before the held ACTIVE session expires. 2. Setup and progression are valid when requested. 3. Delay delivery of the successful progression result until expiry has passed. 4. Let the success continuation publish.
expected: Check Date.now() and the latest exact session immediately before claiming recovered authority; publish FRESH_SESSION_REQUIRED once expired.
actual: The success path calls protocol.observe with the pre-read nowEpochMs and remote snapshot. Only the failure branch rechecks latestNow/latestRemote. A result delivered after expiry still sets ACTIVE_RECOVERED and activeAuthorization=true. The next poll can repair it, but consumers observe expired authority in the meantime.
repro: sweeps/repro/hunt-1018.cjs (expiryDuringRead). Output: `H1018-5 FAIL now>=expiry=true; phase=ACTIVE_RECOVERED; activeAuthorization=true`.
fix idea: Re-resolve the current session and clock on the success path after all awaits, then verify the same session/account/device/rivalry still authorizes the result.
