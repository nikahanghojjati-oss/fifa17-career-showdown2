## Flow map

1. `index.html` owns the seven season facts and `completeSeason` action for each manager.
2. `seasonEngine.js` constructs review UI and supplies the classic entry/review/completion path.
3. `productionSharedSeasonResultsRoute.js` routes the shared transfer completion to season entry.
4. `productionSharedSeasonResults.js` intercepts shared form actions, validates the own form and freezes a review draft.
5. `sparkSharedSeasonResults.js` reads exact provider documents and publishes an immutable own result.
6. `sharedSeasonResults.js` checks season, role, inputs, revisions, receipts and private projections.
7. `sharedSeasonCommit.js` and its production/provider wrappers commit both published results and acknowledgements.
8. Accepted seasons feed `sharedHistoryConvergence.js` and the shared active/closed Showdown adapters.
9. `sharedCareerAnalytics.js` rebuilds career totals, trophies and records from verified projections; abandoned entries contribute nothing.
10. `sparkClosedShowdownCareerLoader.js` walks the career index and caches terminal reads by account.
11. `analytics.js`, `statistics.js`, `trophyRoom.js` and `legacy.js` supply local totals or retain supplied models and choose the shared screen seam.
12. `careerScreenSeam.js` validates model states; `careerScreensV10.js` draws Career Statistics and Trophy Room.
13. `rivalryLegacyV10.js` loads provider career data, caches it by account/manager/pair and draws Rivalry and History.
14. `seasonFinalV10.js` reads reconciliation for the Final Winner and combines rivalry/career frames for Standings.
15. `transferScreenV10.js` adopts existing controls; `productionSharedTransferChallenge.js` builds own guesses/signings.
16. `sharedTransferChallenge.js` and `sparkSharedTransferChallenge.js` enforce phases, locks and hidden opponent inputs until completion.
17. Settings delegates History & Backup to Legacy; `backup.js` exports checksummed storage projections and `importAnalysis.js` validates/migrates them.
18. `restoreUI.js` reviews explicit choices; `restore.js`, `storageTransaction.js`, `storage.js` and Save Library runtime apply/rollback exact bytes.
19. Settings Delete Current Showdown closes the remote pair before clearing local authority; Legacy full reset clears local storage directly.

## Findings

### H1019-1 Keep-current restore replaces the existing Save Library
severity: S1 (local recovery data is lost and the device switches to another Showdown)
status: CONFIRMED (repro below)
where: `js/restore.js:283` (`applyCareerModeRestore`), `js/restore.js:144` (`createCareerModeRestorePlan` destinationIsClean); UI preview/apply in `js/restoreUI.js:104` and `:193`.
steps: 1. Have a migrated, populated Save Library containing local Showdown 1, with the old singleton active slot cleared. 2. Review a valid format-2 backup of Showdown 2. 3. Choose keep-current for active, Legacy, preferences and Save Library. 4. Apply the reviewed restore.
expected: Preview and Apply agree; keep-current writes no replacement library, and Showdown 1 remains active.
actual: Four-slot preview says `saveLibrary=keep-current` with an empty candidate. Apply captures the complete four-slot snapshot but passes the three-slot `currentRaw` to the planner. Missing saveLibrary plus null singleton active is treated as a clean destination. Apply changes the plan to `full-restore-clean`, forces backup active selection, and successfully replaces Showdown 1's library with Showdown 2's. Other local saves/profiles in the replaced registry would be removed as well; remote deletion was not tested.
repro: `sweeps/repro/hunt-1019-restore.cjs` — `H1019-1 CONFIRMED: preview=keep-current, apply=full-restore-clean, local save 1 replaced by backup save 2`
fix idea: Plan Apply from `completeRaw`; require the final plan to honor the choices and reviewed candidate. Add coverage for populated migrated libraries with null singleton active slots.
rule check: Rule Book backup/recovery intent and the explicit keep-current choice are contradicted. The scoring panel does not affect restore choices; no arithmetic discrepancy is claimed.

### H1019-2 Verified restore commits an invalid library and reports success
severity: S1 (valid local saves are overwritten and the device cannot load its active save)
status: CONFIRMED (repro below)
where: `js/importAnalysis.js:305` (`analyzeSaveLibraryRecord`), `js/restore.js:168` (`createCareerModeRestorePlan`), `js/restore.js:306` and `:327` (`applyCareerModeRestore`).
steps: 1. Start with a valid populated Save Library. 2. Review a checksummed format-2 backup whose library is `{schemaVersion:1,activeSaveId:"save_ffffffffffffffffffffffff",profiles:[],saves:[]}`. 3. Explicitly choose Use backup / replace Save Library. 4. Apply.
expected: Reject the dangling activeSaveId before any writes, preserve existing raw bytes, and never describe an unusable registry as successfully restored.
actual: Import analysis checks only top-level shape and entry saveId strings, not foundation identity/reference invariants or nested Showdowns. The real foundation rejects this fixture, but analysis returns ready. The full-library path commits it before validation through runtime activation. Activation fails; restore only adds a warning and returns `ok=true,status=success`. The previous valid library is gone, runtime readiness is false, and `loadSavedShowdown()` returns null. A valid checksum proves byte integrity, not semantic validity. This issue also occurs with explicit replacement and is independent of H1019-1's keep-current mismatch.
repro: `sweeps/repro/hunt-1019-restore.cjs` — `H1019-2 CONFIRMED: invalid library analysis=ready, restore=success, previous save lost, runtimeReady=false`. An expected console diagnostic states that Save Library runtime authority is not ready.
fix idea: Run foundation validation and supported nested-record validation during analysis and again on the complete candidate before storage mutation. Handle post-commit readiness failure as a recovery outcome with preserved recoverable data, not simple success.
rule check: Rule Book's recovery path requires usable saved data. The scoring panel is irrelevant to checksum/schema validation; no scoring changes requested.

### H1019-3 Next-season form retains the previous published results
severity: S2 (wrong season facts and checked trophies are shown as editable new input)
status: CONFIRMED (repro below)
where: `js/productionSharedSeasonResults.js:119` (`pssrRenderEntry`), `:128` (`pssrRender`), `:156` (`pssrOpen`); compare `js/seasonEngine.js:291` and `:347` (`openSeasonEntry`, `resetSeasonEntryFields`).
steps: 1. Open shared season 1 with an own published result: position 1, 102 points, 120 goals, all four trophies/awards checked. 2. Advance the authoritative context to season 2 with completed transfers and no own result. 3. Open shared results. 4. Tap Review and Publish without editing.
expected: A different season/save context starts with blank numeric fields and unchecked achievements; a same-season draft can be retained.
actual: The context change clears only `draft`, not controls. With no own result, rendering enables the existing form. Shared `open` navigates directly, bypassing the classic field-reset path. Season 2 still shows 102 and checked trophies. The real production adapter sends those season-1 facts as the season-2 publish payload after two taps. The provider is a memory spy, so a live database write or a wrong accepted score is not claimed.
repro: `sweeps/repro/hunt-1019-season.cjs` — `H1019-3 CONFIRMED: opening empty season 2 retains season 1 values and checked trophies; two taps republish them as season 2`
fix idea: Reset all seven controls on a new save/rivalry/season form context before populating the current context's own result, retaining only a draft belonging to that exact context.
rule check: Both Rule Book and panel assign trophies and performance bonuses to the entered season. Carrying earlier facts is an input-state bug; the score formula itself is unchanged.

### H1019-4 Older career load overwrites newer accepted-season totals
severity: S2 (cached career state regresses and screens can disagree)
status: CONFIRMED (repro below)
where: `js/rivalryLegacyV10.js:141` (`rlLoadCareerModel`), especially `:159` (`careerCache` assignment); downstream consumers in `js/careerScreensV10.js`, `js/seasonFinalV10.js`.
steps: 1. Under the same account/manager/pair, start a career load with a one-accepted-season snapshot. 2. Start another load after the snapshot advances to two accepted seasons. 3. Let the newer load resolve first, then the older load. 4. Read cachedCareerModel.
expected: Once the latest request publishes the two-season model, an older request must not replace that shared cache.
actual: Both calls pass the same account/manager/pair context check. The newer cache contains two seasons, then the older call overwrites it with one. Per-screen refresh tokens do not protect the cache write inside rlLoadCareerModel, and direct career loads also use this method. Cached Stats/Trophy/Standings readers can regress while a newer History read remains current. Repro uses deferred provider responses with real verified career projections; provider storage is not altered.
repro: `sweeps/repro/hunt-1019-career.cjs` — `H1019-4 CONFIRMED: overlapping career loads settle 2 then 1; cached accepted seasons regress from 2 to 1`
fix idea: Guard shared career-cache publication with a loader generation/token covering every caller, and retain the existing account/manager/pair check. Consider accepted revision ordering so a stale snapshot cannot supersede newer accepted data.
rule check: Rule Book career accumulation and the panel's season facts require consistent accepted data. This changes displayed totals through a race, not through scoring arithmetic.

### H1019-5 Abandoned-only career is unavailable in Statistics but ready in Trophy Room
severity: S2 (valid readable career state is shown as unavailable)
status: CONFIRMED (repro below)
where: `js/careerScreensV10.js:28` (`v10Pick`), `:44` (`v10CareerStatistics`), `:78` (`toV10Frame`); source state from `js/sharedCareerAnalytics.js` and `js/careerScreenSeam.js`.
steps: 1. Load a ready career index containing one abandoned Showdown and no counted seasons. 2. Build the real shared career model. 3. Convert it to the Career Statistics and Trophy Room frames.
expected: Both screens retain a valid zero-contribution career state; absent season records/averages remain no-data placeholders. Abandoned results contribute nothing.
actual: Analytics correctly returns ready with zero totals and null best-season/average fields. The seam accepts it. Statistics' v10Pick requires every requested field to be finite, rejects those legitimate nulls, and turns the whole frame unavailable. Trophy Room remains ready with zero totals because it requests only counters. This is a state-conversion defect, not a wording/layout finding.
repro: `sweeps/repro/hunt-1019-career.cjs` — `H1019-5 CONFIRMED: abandoned-only career, Stats=unavailable versus Trophy Room=ready and zero totals`
fix idea: Permit legitimate nullable record/average fields in the Statistics frame and use the renderer's no-record placeholder, or supply a consistent valid no-counted-season state across both screens without counting abandoned seasons.
rule check: Factory rule 7 explicitly excludes abandoned Showdowns from totals. Zero contribution is correct; unavailable is the defect. Neither Rule Book nor scoring panel calls for invented record values.
