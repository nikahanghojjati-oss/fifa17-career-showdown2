# SHOWDOWN VISUAL — SCREEN BLUEPRINT STANDARD V5
Status: ACTIVE SOL->LUNA BUILD CONTRACT

## Purpose

Luna should not receive vague art direction.

Every screen build must be preceded by a Sol-authored blueprint containing the following sections.

## A. Screen story

One sentence describing what the player should feel and understand.

Example:
`PRIVATE GUESS WAR ROOM — the deadline is over; each manager now secretly predicts the rival's signings.`

## B. Dominant visual object

Exactly one primary object/hierarchy anchor.

Examples:
- wheel
- pack theatre
- private guess board
- score confrontation
- trophy
- results table

If this cannot be named, the composition is not ready.

## C. Visual reference extraction

For each relevant reference, state:
- what to borrow;
- what NOT to copy.

Never send Luna a raw folder and ask it to "make something like this."

## D. Exact asset manifest

List exact asset IDs/paths and role.

Each item must be one of:
- REQUIRED
- OPTIONAL
- FORBIDDEN
- IDENTITY-ANCHOR-ONLY

For character art, identify the screen-specific pose asset.

If a required pose asset does not exist:
`ASSET BLOCKER — DO NOT SUBSTITUTE A HOME/GENERIC HERO.`

## E. Geometry

Specify desktop geometry numerically enough to prevent drift:
- canvas target;
- shell height;
- content max width;
- hero left/right anchor zones;
- dominant-object width/height range;
- safe center interaction zone;
- title zone;
- CTA zone;
- maximum dead-space bands;
- overlap rules.

Luna may fine-tune within the ranges but may not replace the composition architecture.

## F. Typography

Define roles:
- display title;
- functional condensed text;
- personality script.

Provide size ranges and casing behavior.

No proprietary font requirement. Recreate energy with rights-safe type, weight, tracking, skew, texture and shadow.

## G. Palette/material tokens

Define:
- background black;
- graphite panel;
- warm gold;
- bright CTA gold;
- cream text;
- muted text;
- error accent.

Also define:
- border thickness;
- corner geometry;
- shadow/glow restraint;
- texture/diagonal treatment.

## H. State variants

For each product state:
- status headline;
- visible own data;
- visible peer data;
- primary action;
- disabled/locked behavior;
- decorative changes only.

No state inference by Luna.

## I. Mobile recomposition

Write a separate layout plan for 390×844.

Explicitly say:
- which desktop assets disappear;
- order of content;
- touch target minimum;
- full-width actions;
- overflow requirement;
- whether shallow character crops are allowed.

## J. Forbidden patterns

Every blueprint includes concrete rejection rules:
- SaaS/dashboard composition;
- generic card grid;
- avatar chips replacing cinematic identity;
- giant blank form surfaces;
- copied reference data;
- unapproved hero substitution;
- baked live text;
- invented product actions;
- desktop shrink-on-mobile.

## K. Browser proof

Luna must check only the bounded matrix Sol names.

Sol then independently rechecks:
1. visual-family fidelity;
2. composition;
3. asset correctness;
4. product/state correctness;
5. mobile;
6. accessibility;
7. final polish.

Luna's self-rating is advisory only.

## L. Revision discipline

If the architecture fails, do not patch it with five CSS nudges.

Sol returns a structural delta.

If only polish fails, return the smallest visual correction.

After two repeated failures of the same class, Sol rewrites the relevant blueprint section before asking Luna again.
