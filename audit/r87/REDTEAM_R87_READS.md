## Billing method

A server document delivery costs one document plus the distinct Rules dependencies evaluated for that request; each server listener delivery pays again, cache deliveries pay zero, and writes pay their evaluated Rules dependencies. Costs below distinguish the repository's conservative lookup-table model from a branch actually reached. Repeated identical dependency paths inside one Rules evaluation are not added twice. Requests in separate transactions do not share that discount.

The current composed Rules/table pin passes `r86-billed-counter-contracts.cjs`. The table is an upper bound over helper branches and symbolic write paths, not an execution trace. In particular, finding A-04 explains a discrepancy in the finished root price. No denied-request or offline-attempt bill is invented where the evaluated Rules branch is unknown.

## Findings

### R87-A-01 — P2: a failed summary get becomes a full archive read

- **Evidence:** `js/sparkClosedShowdownCareerLoader.js:70-79` catches *every* `loadSummary()` error except cancellation, sets `kept=null`, and invokes the full reader. `js/careerSummaryStore.js:104-106` deliberately throws on failed get; its comment explicitly distinguishes a failed get from a missing summary. `js/sparkCompletedShowdownReader.js:166-190` reads root, setup and four documents per season.
- **Trigger:** open History/Statistics/Trophy Room/Rivalry/Legacy on a phone lacking that game's local summary (new phone, evicted/blocked IndexedDB), with a summary already in Firebase. A transient failure of that one summary request, followed by restored connectivity, makes the archive read succeed. A summary-specific Rules rollout failure has the same fallback. This is separate from the already-fixed permanent-invalid-game reread.
- **Waste:** the failed request's own charge is **unknown**. The unnecessary successful fallback sends `2 + 4S` document reads. At closed prices, setup is 3, each season is `3 + 4 + 4 + 3 = 14`, and root is 2 on its first allowing branch (A-04): **`5 + 14S` billed reads**. Thus S=1/3/5/10 gives **19/47/75/145** additional reads per affected game/open, versus retrying the 2-read summary. The current table reports **20/48/76/146** instead. Both phones encountering this once doubles those numbers. No fixed per-season rate: multiply by affected games/recovery occurrences. If all N ten-season summaries fail this way, additional successful fallback traffic is `145N`: 1,450/4,350/14,500 at N=10/30/100, excluding failed-request charges and subsequent writes.
- **Proof run:** reused the real fixture constructor and VM modules from `tests/contracts/r86-career-summary-scale-contracts.cjs`; first loaded a valid ten-season game to create its summary, then opened a new fake phone and made only `/careerSummary/` gets reject with `unavailable`. Output: **`summary-error fallback 44 gets 42 archive gets`** (index + failed summary + 42 successful archive gets). Only SDK I/O was fault-injected; loader/reader/store were unchanged.
- **Smallest fix:** preserve a failed-summary outcome and offer a bounded retry of that summary; enter the full reader only after a successful missing/incompatible-summary response. Preserve cancellation and existing model availability handling.

### R87-A-02 — P2: reading the rivalry pays a lookup of itself

- **Evidence:** `firestore.spark.rules:443-448` `currentlyEntitled()` obtains `get(/rivalries/$(rivalryId))`; the root's own `allow get` at `firestore.spark.rules:937` calls it. Additional root read alternative: `firestore.persistent-pair-production.fragment.rules:549-550` obtains the same root in `cmsCompletedShowdownReadable()`.
- **Trigger:** every successful root read/listener delivery during normal paired play, including startup, progression and close observation. This is a Rules cost, even when the application performs just one document read.
- **Waste:** **1 billed lookup per root request/delivery**. For R root deliveries per season across the two phones, savings = **R reads/season**; for R/hour, R/hour. R was not instrumented in this audit, so no percentage of 2,378 is asserted. Cached deliveries save zero because they already cost zero.
- **Proof:** on the root match, `resource` is exactly the document at the path passed into the helper. The lookup table records a live root as one lookup (2 billed total). This is also visible through `CareerModeFirestoreBudget.rulesLookups.read('rivalries/pair_a', false) === 1`.
- **Smallest safe fix:** add a root-match-specific entitlement helper taking `resource.data` and perform exactly the existing signed-in/authorized-ID checks against it. For the completed-root alternative, pass that same resource into a version retaining **all** completed witness, slot and active-account checks. Keep `get()` versions for child-document matches. Pending capability access must retain its invite lookup. Do not remove parent checks from child reads or account/device/session checks from writes. This removes exactly the **root get**, with identical read authorization.

### R87-A-03 — P3: verified CLOSED screens still restore the context watch

- **Evidence:** `js/productionSharedTerminalClose.js:57-70` retains a request for a shared shell with a rivalry ID. `:351-364` calls `watchContext(request.rivalryId)` before the terminal refresh guard at `:195-196`. That guard stops the old 45-second provider reread, but does not turn off the watch. `js/sparkPrivatePairing.js:1017-1019`, `:1181-1203` detach on hide and restore watched paths on return; `:1156-1173` bill/attach the root watch. CLOSED roots are not covered by `fsbImmutable()` at `:992-1006`.
- **Trigger:** leave a verified CLOSED Champion/Final Winner shell selected, lock/unlock or hide/show the phone. Its terminal request still exists. Even if only the rivalry watch survives, it is restored for a document whose terminal result is already known. This is **not** a recurrence of the fixed 45-second CLOSED full-provider poll.
- **Waste:** a root server delivery is **2 actual billed reads** (a direct get would be 3 in the counter's finished model; its live-priced listener counter remains 2). With U such returns on each of two phones: **4U reads**; for U returns/hour/phone: **4U/hour**. At no returns and no server changes the attached listener alone generates **0 recurring deliveries/hour**. Session-watch behavior after close depends on remote-session cleanup and is excluded from this minimum.
- **Proof:** request construction has no terminal-state exclusion; `ptcWatchContext()` has only a visibility exclusion; `ptcRefreshNow()` returning CLOSED does not call `watchContext(null)`. The unlock contract verifies the underlying detach/restore behavior, though it does not cover a CLOSED shell.
- **Smallest fix:** stop the context watch after verifying CLOSED/DELETED for the same request key; do not restore it until a different live request is selected. Retain watching for READY/BLOCKED/RECOVERY_PENDING, where a partner can still finish the close.

### R87-A-04 — P3: the finished root price includes an unreachable account lookup

- **Evidence:** `js/sparkPrivatePairing.js:709` (generated root row), `:741`, `:871-877`; table policy in `tests/browser/support/billed-reads-table.json` `liveReadExclusions`. Actual first allow: `firestore.spark.rules:443-448,937`. The extra completed branch is `firestore.persistent-pair-production.fragment.rules:549-576`.
- **Trigger:** direct finished-game root gets, e.g. first career backfill or completed detail read. `fsbMeterGet()` always selects `finished=true`; the generated root row is live=1 lookup / finished=2 lookups.
- **Miscount:** **+1 reported billed read per successful authorized closed-root get**. `currentlyEntitled()` tests membership, not active/closed state, so it still succeeds on a closed root. The account lookup in the completed alternative is never reached. N full completed-game loads overstate by **N** (10/30/100 for those archive sizes); ordinary known-phone summary opens do not read those roots and incur no such bias. **Actual wasted reads: 0**; this is an accounting error and would become irrelevant after A-02 removes the self lookup and regenerates the model.
- **Proof:** the unchanged budget API prints root lookup counts **1 live / 2 finished**. Compare its finished exclusion to the unconditional membership branch, which allows the same authorized account after close. No modified app behavior needed.
- **Smallest fix:** add the account exclusion for authorized root reads after close too, retaining the distinct not-yet-paired case. Regenerate both client and CE2PG tables/tests. Do not count an agreement between these two shared models as independent billing validation.

### R87-A-05 — P3: symbolic write dependencies overcount identical concrete paths

- **Evidence:** `js/sparkPrivatePairing.js:716-717` generated Transfer Challenge rows and `:742` `fsbWriteLookups()`. `:1414-1424` bills that union on successful and answered-failed writes. The corresponding table `writeNotes` explicitly declares a create/update upper bound. `js/sparkSharedTransferChallenge.js:130-132,177` uses the same rivalry ID for public/own-role writes and ledger fields.
- **Trigger:** a normal Transfer War mutation writing the public challenge and own role. The generated dependencies include both `rivalries/{after.rivalryId}` and `rivalries/{rivalryId}`. Both resolve to the very same rivalry, but the counter's Set compares the template strings.
- **Miscount:** probe output: public write=8 symbolic dependencies, role write=5, union=**9**. At least **one** of that union's entries aliases another concrete path, so it cannot represent nine distinct lookup documents: **at least +1 estimated read per such commit**, before accounting for unreachable create/update branches. For M such commits/season, inflation is at least M; total exact bias is **unknown** without a branch trace. Actual unnecessary Firestore traffic: **0**. This affects both the reads display and measured season cost.
- **Proof:** inspect the generated strings or call `rulesLookups.write([publicPath, ownRolePath])`; no replacement Firebase SDK required. The contract asserts the conservative model, not concrete path resolution.
- **Smallest fix:** retain the upper bound as a separately named diagnostic; resolve dependency templates using the actual document path/payload and deduplicate concrete paths for the user estimate. Measure evaluated branches before promising exact bills. Apply the same correction to CE2PG.

### R87-A-06 — P3: “both phones” excludes the other phone's career traffic

- **Evidence:** `js/sparkPrivatePairing.js:825-831` uses `used = 2 * thisPhone.game + thisPhone.career`; `js/settings.js:315` renders those categories. The other phone's counters are neither read nor exchanged.
- **Trigger:** Nik opens career pages while Daniel checks Settings (or vice versa). Normal asymmetrical play suffices; no extra tab or modified client is needed.
- **Miscount:** with equal gameplay G on each phone and career costs C_D/C_N, true use is `2G + C_D + C_N`. Daniel shows `2G + C_D`: missing **C_N**; Nik misses **C_D**. If both spend C on career pages, **each** misses C, rather than counting both. At 10/30/100 finished games, a new phone with summaries spends `1 + 2N` = **21/61/201** billed reads on one career open; these are entirely absent on the partner's meter. A known phone costs only 1, so this is not the old cold-archive-scaling defect. With per-season estimate P, capacity error is exactly `floor((50000-used)/P) - floor((50000-used-C_other)/P)`. It may be zero near some rounding boundaries. Actual wasted reads: **0**.
- **Proof:** direct arithmetic in `fsbSeasonsLeftToday()`. Doubling gameplay is itself an estimate when phones have different waits/reloads. The formula also has no write-quota term, so it cannot guarantee seasons under the separate 20,000-write limit.
- **Smallest fix:** label it explicitly as a phone-derived estimate that excludes the partner's career browsing; use a conservative reserve for a safety claim. Do not introduce a continuously reading cross-phone meter to fix this UI estimate. An exact project-wide remaining quota is **unknown** to this client.
